# Задание 1. Исследование моделей и инфраструктуры

## 1\. Контекст задачи

QuantumForge Software нужна внутренняя система поиска знаний на основе RAG. Компания использует разрозненную базу знаний: Markdown/MDX-файлы в репозиториях, Confluence, PDF-спецификации, Google Docs, Zendesk Guide и другие источники.

Основные пользователи будущего бота:

* разработчики — ищут архитектурные решения, API-документацию и описание микросервисов;
* саппорт — ищет способы решения типовых проблем пользователей;
* менеджеры и аналитики — ищут регламенты и бизнес-правила;
* новые сотрудники — используют onboarding-инструкции.

Основные проблемы:

* документация разрознена и дублируется;
* разные версии одного процесса могут лежать в Confluence, Google Docs и PDF;
* новые инженеры тратят время на поиск нужной информации;
* часть документации быстро устаревает после major-release;
* подготовка к SOC 2 review требует ручной сверки актуальных политик и регламентов.

Цель проекта — создать RAG-бота, который быстро отвечает на вопросы сотрудников по корпоративной базе знаний, показывает источники ответа и честно сообщает, если информации в базе знаний недостаточно.

## 2\. Сравнение LLM-моделей

### 2.1 Локальные Hugging Face модели

Примеры: Llama, Mistral, Qwen, Gemma и другие open-source модели.

**Качество ответов**

Качество зависит от конкретной модели, размера и качества инструкции. Малые модели дешевле в эксплуатации, но хуже следуют сложным инструкциям и чаще ошибаются в длинных корпоративных документах. Более крупные модели дают лучшее качество, но требуют GPU и настройки inference.

**Скорость работы**

На CPU локальные LLM обычно работают медленно. Для нормального пользовательского опыта нужен GPU. Скорость также зависит от размера модели, квантования, контекстного окна и числа одновременных пользователей.

**Стоимость владения и использования**

Прямой оплаты за токены нет, но появляются другие расходы:

* GPU-сервер;
* DevOps/MLOps-поддержка;
* мониторинг;
* обновление моделей;
* настройка безопасности;
* резервирование инфраструктуры.

**Удобство развёртывания**

Развёртывание сложнее, чем у облачного API. Нужно выбрать модель, поднять inference-сервер, настроить лимиты, логирование, мониторинг, обновления и fallback.

**Главное преимущество**

Данные можно оставить внутри инфраструктуры компании. Это важно для security-документов, SOC 2 материалов, внутренних архитектурных решений и клиентских спецификаций.

\---

### 2.2 Облачные OpenAI модели

Примеры: GPT-4.1 mini или другой актуальный low-cost model через OpenAI API.

**Качество ответов**

Облачные модели OpenAI обычно дают высокое качество для RAG-сценариев: хорошо следуют инструкциям, умеют суммаризировать, объяснять и работать с контекстом. Для MVP это один из самых быстрых способов получить рабочий результат.

**Скорость работы**

Скорость хорошая для прототипа и небольшого production. Не нужно поднимать собственную ML-инфраструктуру. Ограничения зависят от API-лимитов, сети и выбранной модели.

**Стоимость владения и использования**

Оплата идёт за токены. Например, для GPT-4.1 mini указана стоимость за 1M input/output tokens. Для embeddings `text-embedding-3-small` указана цена $0.02 за 1M tokens. Для учебного проекта это дешёвый и простой вариант.

**Удобство развёртывания**

Самый простой вариант:

* получить API key;
* подключить SDK;
* настроить переменные окружения;
* добавить обработку ошибок и лимитов.

**Главный риск**

Тексты документов отправляются во внешний облачный API. Для конфиденциальных документов это требует согласования с ИБ, Legal и владельцами данных.

\---

### 2.3 Облачные YandexGPT модели

**Качество ответов**

YandexGPT может быть хорошим вариантом для русскоязычных корпоративных сценариев и компаний, которые уже используют Yandex Cloud. Качество зависит от конкретной модели и режима использования.

**Скорость работы**

Скорость зависит от выбранной модели, региона, API-лимитов и режима работы. Для MVP API-подход удобен, потому что не требует локального GPU.

**Стоимость владения и использования**

Стоимость считается по токенам и зависит от выбранной модели. Для точной оценки нужно смотреть актуальный прайс Yandex Cloud AI Studio на момент внедрения.

**Удобство развёртывания**

Развёртывание проще локальной LLM: используется облачный API. Но если компания уже живёт в AWS, добавление ещё одного облачного провайдера может усложнить security review и эксплуатацию.

**Главный риск**

Как и в случае с OpenAI, документы уходят во внешний облачный сервис. Для закрытых материалов нужен отдельный процесс согласования.

|Скорость|Нужен GPU для комфортной работы|Быстрый старт через API|Быстрый старт через API|

**Вывод по LLM**

Для учебного MVP лучше использовать облачную LLM, потому что она быстрее даёт рабочий результат и не требует GPU. Для реального production в QuantumForge лучше использовать гибридный подход: облачная модель для некритичных документов и локальная LLM для конфиденциальных материалов.

## 3\. Сравнение моделей эмбеддингов

### 3.1 Локальные Sentence-Transformers

**Скорость создания индекса**

На небольшом объёме документов скорость нормальная даже на CPU. Для большой базы знаний, особенно с регулярной переиндексацией, лучше использовать GPU или отдельный indexing worker.

**Качество поиска**

Качество зависит от выбранной модели. Для QuantumForge нужно выбирать multilingual-модель, потому что в документации могут быть английские и русские материалы. Для поиска по техническим текстам лучше протестировать несколько моделей на реальных вопросах.

**Стоимость владения и использования**

Нет оплаты за API-токены. Основные расходы — CPU/GPU, хранение индекса, поддержка пайплайна индексации.

**Плюсы**

* документы не уходят во внешний API;
* можно использовать внутри закрытого контура;
* хорошо подходит для конфиденциальных материалов.

**Минусы**

* нужно выбирать и тестировать модель;
* качество может быть ниже, чем у сильных облачных embeddings;
* нужна поддержка локального ML-runtime.

\---

### 3.2 OpenAI Embeddings

Пример: `text-embedding-3-small`.

**Скорость создания индекса**

Быстрый старт через API. Не нужно поднимать локальную модель. На скорость влияют API-лимиты, батчинг, сеть и объём документов.

**Качество поиска**

Хорошее качество для general-purpose semantic search. Подходит для MVP, где важна скорость разработки и стабильность результата.

**Стоимость владения и использования**

Стоимость считается по токенам. Для учебного проекта стоимость низкая, особенно при небольшом наборе документов. Для production стоимость будет зависеть от объёма базы знаний и частоты переиндексации.

**Плюсы**

* быстро подключить;
* не нужен GPU;
* хорошее качество поиска;
* удобно для учебного MVP.

**Минусы**

* документы отправляются во внешний API;
* для чувствительных документов нужен security approval;
* есть зависимость от внешнего провайдера.

**Вывод по embeddings**

Для проектной работы выбирается OpenAI Embeddings, потому что это самый быстрый способ получить рабочий RAG. Для production в QuantumForge лучше рассмотреть локальные Sentence-Transformers для конфиденциальных документов.

## 4\. Сравнение векторных баз: FAISS и ChromaDB

### 4.1 FAISS

FAISS — библиотека для эффективного similarity search и clustering dense vectors. Она хорошо подходит для локального MVP, потому что не требует отдельного сервера и может работать прямо внутри приложения.

**Скорость поиска и индексации**

FAISS быстрый и эффективный. Поддерживает разные типы индексов и GPU-ускорение. Для учебного проекта достаточно простого локального индекса.

**Сложность внедрения и поддержки**

Для MVP внедрение простое. Но в production нужно дополнительно решать:

* версионирование индекса;
* обновление документов;
* хранение метаданных;
* backup;
* пересборку индекса;
* синхронизацию индекса с источниками документов.

**Удобство в работе**

FAISS удобен как библиотека, но это не полноценная прикладная vector database с развитым управлением коллекциями и метаданными.

**Стоимость владения**

Минимальная для MVP: не нужен отдельный сервис, достаточно локального диска. Для production стоимость зависит от выбранной схемы хранения и обновления индекса.

\---

### 4.2 ChromaDB

ChromaDB — open-source vector database, ориентированная на AI/RAG-приложения. Она поддерживает коллекции, документы, embeddings и метаданные.

**Скорость поиска и индексации**

Для MVP и среднего объёма данных скорости достаточно. ChromaDB удобнее, когда нужны коллекции, метаданные, фильтрация и более прикладная работа с документами.

**Сложность внедрения и поддержки**

Сложнее FAISS, потому что это уже отдельная база/сервис. Но для production она может быть удобнее, так как предоставляет больше готовых возможностей вокруг хранения и поиска.

**Удобство в работе**

ChromaDB удобнее для RAG-приложений:

* коллекции;
* метаданные;
* хранение документов;
* фильтрация;
* локальный или cloud-вариант.

**Стоимость владения**

Для локального варианта — стоимость сервера и поддержки. Для cloud-варианта — managed-стоимость. В production это может быть оправдано, если нужны масштабирование и эксплуатационная зрелость.

\---

### 4.3 Итоговое сравнение vector DB

|Критерий|FAISS|ChromaDB|
|-|-|-|
|Скорость поиска|Очень высокая|Хорошая|
|Индексация|Быстрая, простая для MVP|Удобная, особенно с коллекциями|
|Сложность внедрения|Низкая|Средняя|
|Поддержка метаданных|Нужно организовывать отдельно|Есть из коробки|
|Удобство для учебного проекта|Отлично|Можно, но избыточно|
|Удобство для production|Требует доработок вокруг эксплуатации|Лучше подходит как прикладная vector DB|
|Стоимость MVP|Минимальная|Выше, если поднимать как сервис|
|Стоимость production|Зависит от обвязки|Зависит от self-hosted/cloud варианта|

**Вывод по vector DB**

Для проектной работы выбирается FAISS. Он проще, быстрее внедряется и не требует отдельной инфраструктуры. ChromaDB лучше рассматривать как следующий шаг для production, если появятся требования к коллекциям, метаданным, фильтрации, ролям и регулярному обновлению индекса.

## 5\. Рекомендуемая конфигурация сервера

### 5.1 Для учебного MVP

Подходит для варианта с облачной LLM и облачными embeddings.

```text
CPU: 2–4 vCPU
RAM: 8 GB
GPU: не требуется
Disk: 20–40 GB SSD
```

Что работает на сервере:

* Telegram-бот;
* загрузка документов;
* построение FAISS-индекса;
* retrieval;
* вызовы внешней LLM через API.

Это лучший вариант для сдачи проектной работы.

\---

### 5.2 Для production с локальными embeddings

```text
CPU: 4–8 vCPU
RAM: 16–32 GB
GPU: опционально
Disk: 50–100 GB SSD
```

Подходит, если компания хочет строить embeddings внутри своего контура, но генерацию ответа пока оставляет в облачной LLM.

\---

### 5.3 Для production с локальной LLM

```text
CPU: 8–16 vCPU
RAM: 64 GB
GPU: NVIDIA GPU 16–24 GB VRAM
Disk: 100–200 GB SSD/NVMe
```

Подходит, если компания не готова отправлять документы во внешние LLM API. Это самый дорогой и сложный вариант.

## 6\. Варианты решения для QuantumForge

### Вариант 1. Минимальный учебный MVP

```text
LLM: OpenAI API
Embeddings: OpenAI text-embedding-3-small
Vector DB: FAISS
Interface: Telegram Bot
Runtime: Docker Compose
```

**Плюсы**

* быстро реализовать;
* не нужен GPU;
* низкая инфраструктурная сложность;
* хорошо подходит для сдачи проектной работы;
* FAISS достаточно для локального индекса.

**Минусы**

* документы отправляются во внешний API;
* не подходит для конфиденциальных данных без согласования;
* FAISS требует ручной организации обновления индекса.

**Оценка**

Лучший вариант для учебного проекта.

\---

### Вариант 2. Локальный privacy-first

```text
LLM: локальная Hugging Face модель
Embeddings: Sentence-Transformers
Vector DB: FAISS
Interface: Telegram Bot
Runtime: GPU server
```

**Плюсы**

* данные остаются внутри компании;
* подходит для security-документов и SOC 2 материалов;
* нет оплаты за токены внешнему API.

**Минусы**

* нужен GPU;
* сложнее поддержка;
* дольше разработка;
* качество ответов нужно отдельно тестировать.

**Оценка**

Хороший production-вариант для sensitive data, но избыточен для учебной сдачи.

\---

### Вариант 3. Корпоративный managed-вариант

```text
LLM: OpenAI или YandexGPT
Embeddings: OpenAI Embeddings или аналог Yandex
Vector DB: ChromaDB
Interface: Telegram / Slack bot
Runtime: Kubernetes
```

**Плюсы**

* удобнее масштабировать;
* ChromaDB лучше подходит для коллекций и метаданных;
* проще развивать в сторону полноценной корпоративной базы знаний.

**Минусы**

* выше инфраструктурная сложность;
* нужно согласование облачного провайдера;
* дороже для MVP.

**Оценка**

Хороший вариант для следующего этапа после MVP.

\---

### Вариант 4. Гибридный production-подход

```text
LLM: cloud LLM для некритичных документов + local LLM для sensitive data
Embeddings: локальные Sentence-Transformers для sensitive data
Vector DB: ChromaDB или FAISS
Interface: Slack / Telegram / Web UI
Runtime: Kubernetes
Security: RBAC, audit logs, document classification
```

**Плюсы**

* баланс качества, безопасности и стоимости;
* чувствительные документы не уходят во внешний API;
* можно масштабировать на разные источники знаний;
* лучше подходит для реальной компании.

**Минусы**

* самая сложная архитектура;
* нужна классификация документов;
* нужны роли, аудит, разграничение доступа;
* больше времени на внедрение.

**Оценка**

Лучший production-вариант для QuantumForge, но не лучший для учебного MVP.

## 7\. Итоговая рекомендация

### Для проектной работы

Выбирается следующая конфигурация:

```text
LLM: OpenAI API
Embeddings: OpenAI text-embedding-3-small
Vector DB: FAISS
Interface: Telegram Bot
Runtime: Docker Compose
Server: 2–4 vCPU, 8 GB RAM, без GPU
```

**Почему этот вариант лучший для сдачи**

1. Он быстрее всего позволяет получить рабочий RAG-бот.
2. Не нужен GPU и сложная ML-инфраструктура.
3. FAISS прост в использовании и подходит для локального MVP.
4. OpenAI Embeddings дают хорошее качество поиска при низкой стоимости на небольшом объёме данных.
5. Telegram Bot соответствует требованию тарифа Pro.
6. Docker Compose достаточно для демонстрационного запуска.

\---

### Для реального production в QuantumForge

Рекомендуется гибридная архитектура:

```text
Неконфиденциальные документы:
cloud LLM + cloud embeddings

Конфиденциальные документы:
local embeddings + local/private LLM

Vector DB:
ChromaDB или FAISS с отдельной обвязкой

Security:
RBAC, аудит запросов, классификация документов, контроль источников
```

**Почему не стоит сразу использовать только облако**

В базе знаний есть архитектурные документы, security-политики, SOC 2 материалы, спецификации клиентов и внутренние регламенты. Такие данные нельзя автоматически отправлять во внешний LLM API без согласования с ИБ и владельцами данных.

**Почему не стоит сразу делать полностью локальную LLM для учебного проекта**

Это сильно увеличит сложность, потребует GPU и не даст преимущества для сдачи MVP. Для учебного проекта важнее показать корректную RAG-логику: загрузка документов, индексация, retrieval, генерация ответа, источники и честный отказ при отсутствии данных.

## 8\. Финальный выбор

Для реализации проектной работы выбираю:

```text
FAISS как векторную базу
OpenAI Embeddings для построения индекса
OpenAI LLM для генерации ответа
Telegram Bot как пользовательский интерфейс
Docker Compose для запуска
```

FAISS выбран потому, что он быстрый, простой, не требует отдельного сервера и подходит для локального MVP. ChromaDB сильнее для production-сценариев с коллекциями, метаданными и фильтрацией, но для текущей проектной работы будет избыточной.
